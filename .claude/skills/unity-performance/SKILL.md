# 성능

> 마지막 갱신: 2026-09-06 (Phase 1 진행 중)

## ⚠️ 측정하기 전에 최적화하지 않는다

**이 문서에서 가장 중요한 줄이다.** 2D 메트로배니아 1인 프로젝트에서 성능이 실제 문제가 되는
시점은 Phase 8~9(콘텐츠 대량 생성) 이후다. 그 전에 하는 최적화는 대부분 코드만 복잡하게 만들고
효과가 없다. **Profiler 수치 없이 "느릴 것 같아서" 구조를 바꾸지 않는다.**

문제가 생기면 순서는 항상: 재현 → Profiler로 측정 → 원인 특정 → 그 지점만 수정 → 재측정.

## 이미 정해진 것 (성능 때문이 아니라 다른 이유로 정해졌지만 성능에도 영향)

| 결정 | 성능상 의미 |
|---|---|
| 타일맵에 **Composite Collider 2D** + `Rigidbody2D(Static)` (Phase 2) | 타일마다 콜라이더가 생기는 걸 하나로 병합. 원래 목적은 "타일 경계 걸림 제거"지만 콜라이더 수도 크게 줄인다 |
| 맵 1개 = 씬 1개 | 한 번에 로드되는 범위가 자연히 제한된다 |
| 씬 전환 **비동기 로드** (Phase 2) | 로딩 중 프레임 정지 방지 |
| `GetComponent`를 `Awake`에서 캐싱 | → `unity-csharp` |

## WebGL 제약 (배포 대상 후보)

빌드 모듈이 Windows Standalone과 **WebGL 둘 다 설치되어 있다.** WebGL로 낼 생각이 있다면
Phase 9 이전에 한 번 빌드해봐야 한다 — 다운로드 용량과 초기 로드가 데스크톱과 전혀 다른 문제다.
구체적 절차는 unity 플러그인 `optimize-web` 스킬.

## GC 압박을 만드는 패턴 (Phase 3부터 실제로 문제가 됨)

`Update`/`FixedUpdate`처럼 매 프레임 도는 곳에서:

- `new List<>()`, `new` 배열, 문자열 결합(`+`), LINQ → 매 프레임 쓰레기 생성
- `GetComponent`, `FindObjectOfType`, `Camera.main` → 캐싱할 것
- `Physics2D.OverlapBox`(할당 버전) → 자주 부르면 `OverlapBoxNonAlloc` 계열 고려. **단, 접지 판정 1회/프레임 수준이면 지금은 문제 아니다**

## 아직 정해지지 않은 것

- [ ] **Phase 3** — 적·투사체 오브젝트 풀링을 도입할지. 적이 동시에 몇 마리 나오는지 정해진 뒤 판단
- [ ] **Phase 8** — 스프라이트 아틀라스 구성 단위 (지역별? 용도별?). 아틀라스가 커지면 씬 전환마다 통째로 로드된다
- [ ] **Phase 9** — 목표 프레임과 대상 사양. 이게 없으면 "빠르다"의 기준이 없다
- [ ] **Phase 9** — WebGL로 낼지 결정 → 내면 다운로드 용량 예산도 여기 적는다

## 이 문서를 갱신하는 시점

**실제로 느려진 걸 측정한 뒤에만.** 측정값(어디서 몇 ms)과 바꾼 내용, 재측정 결과를 함께 적는다.
측정 없이 추측으로 항목을 늘리지 않는다.
